# CampusQ Firestore schema — Phase 3 design
Target approved by developer: new CampusQ project, Standard edition, Native/Core API, database `(default)`, region `asia-southeast1` (Singapore). **Not provisioned or verified remotely.** This choice takes precedence over skill provisioning defaults. Validate edition/location through CLI after authorization.

## Shared conventions
All top-level records have `schemaVersion:1` (integer), `createdAt`, `updatedAt` (server Timestamp), except immutable records which omit updatedAt. IDs are immutable random Firestore IDs (<=128 chars, never display names) unless a deterministic ID is specified. Auth UID is the owner identity; university student number is never an authorization key. Foreign keys are immutable document-ID strings validated by trusted backend existence checks. Names/emails in existing UI models are display data, not authority.

Dates/times: UTC Timestamp for instants, institution timezone `Asia/Manila` and server-derived `businessDate:YYYY-MM-DD`. Singapore is data location, not business timezone. No client-formatted time strings stored as authoritative values. Server calculates wait estimates and the client formats instants. Timestamp server origin must be enforced on later client writes. Every command uses a validated idempotency key, actor UID, expected version and server timestamps.

Common validation: reject unknown fields in commands; trim strings, reject control characters; names1–120, descriptions1–2000, messages1–2000, emails<=254 (Auth email authoritative), IDs1–128 with no slash, requirements<=30 each1–300, settings maxDailyQueueLimit1–10000. Integers must be integers, not fractional/coerced. Dates valid and within an agreed booking horizon; references/ownership/version immutable. Required fields cannot disappear on update. Future server validators must apply equally to create/update; schema documentation alone does not validate Admin SDK writes.

Queue statuses match existing UI: WAITING, CALLED, SERVING, COMPLETED, SKIPPED, NO_SHOW, CANCELLED, EXPIRED. ## Additional private coordination records (proposed, not implemented)
- `activeQueueLocks/{uid}`: current ticketId (one active queue per student). Server-only, acquired/released with ticket mutation.
- `appointmentSlotLocks/{serviceId_slotEpoch}`: appointmentId, ownerUid, startsAt, endsAt. Service capacity1 initially; one lock per smallest schedule quantum spanned by an appointment.
- `studentSlotLocks/{uid_slotEpoch}`: same slot ownership to prevent cross-service student overlap.
- `studentNumberReservations/{normalizedNumberHash}`: uid (server-only). Canonicalization policy and PII handling must be agreed.
- `commandReceipts/{uid_requestId}`: command type, payload hash, result entityId, expiry; reject reused key with different payload.
- Future `users/{uid}/deviceTokens/{tokenHash}`: token, platform, updatedAt; server-scoped registration/revocation, never public list.
Catch-all rules deny all these paths today.

## Reliable queue operations (design only)
joinQueue callable verifies Auth, active user, trusted claims/authorization version, service flags and institution schedule. In one Firestore transaction read receipt, service/settings, activeQueueLock and daily queueCounter; verify limit, increment sequence, create ticket and lock, record receipt/audit. Retry returns original result. Order WAITING by server sequence within service/day, tie-break document ID. Multiple services are separate queues; do not sort display numbers globally. Call-next transaction claims selected WAITING ticket and staff/counter occupancy, checks expected version and current assignment. Cancel/terminal transition releases locks and upserts transaction atomically. Notifications use outbox/receipt idempotency, not inside a transaction callback with side effects. The institution must confirm whether the daily limit is per service or registrar-wide; a registrar-wide policy needs an additional global daily admission counter in the same transaction. Daily single-counter contention is acceptable only after load testing registrar throughput; scaling requires a new ordering design, not uncoordinated sharded numbers.

## Appointment conflict protection (design only)
Book/reschedule transaction reads service/settings, all relevant service+student quantum locks and receipt. Validate future time, operating days, horizon, slot alignment, duration and capacity. Acquire every affected lock and appointment together. Reschedule atomically releases old locks and acquires new ones; failure retains original. Cancellation releases only locks still owned by that appointment; check-in/start/completion policy defines retention. Duplicate/retry yields same receipt. No query-before-write conflict detection alone and no client authority. Use server time and a DST-aware timezone implementation. Emulator tests currently validate denial, not this unimplemented concurrency algorithm.

## Queries and indexes
`firestore.indexes.json` contains proposed composites for service/day/status/sequence queue order, owner queue history, owner appointment start order, service/status/start appointment management, owner transactions/completion, owner notifications/creation, actor audit/creation. Service catalog uses name ascending limit100 (single-field automatic index); future pagination uses stable document-ID cursor. Queries must include ownerUid for students, assignment/service scope for staff, bounded limits<=100. Public aggregate displays require deidentified server projections, never full ticket collection.

Index exemptions remove email/body/changes from indexing; profile PII/retention exemptions need review before deployment. No indexes deployed, no production query/rules compatibility claimed. Emulator doesn't prove composite-index availability; deploy/test against a configured non-production project later.
