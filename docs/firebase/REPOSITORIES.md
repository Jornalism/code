# Repository boundary
CampusQViewModel still constructs/injects DemoRepository. Its synchronous demo mutations remain unchanged. It observes CampusQStateSource so state ownership has a named interface without forcing network work into synchronous functions. DemoRepository implements that contract; all 23 screens and navigation are unchanged.

ServiceCatalogRepository is a separate suspend boundary. DemoServiceCatalogRepository reads the same shared StateFlow; FirebaseServiceCatalogRepository performs a bounded, server-only one-shot read and strict mapping. It does not subscribe to live queues, swallow backend errors, fall back to demo fixtures or mutate data. Closed rules intentionally deny its request today. Pagination and loading/error presentation are future feature work; this initial 100-record read is not a complete production catalog implementation.

FirebaseBackend requires genuine generated configuration and explicit database/region and is never selected by the app. LocalFirebaseBackend in debug uses a named emulator-only Firebase app, auth/firestore/functions routed before use, and memory-only cache. FCM dependency is present for later work; automatic initialization is disabled. No registration/login/token refresh/role provisioning/callable business operation is added.

Later phases should add feature-scoped asynchronous interfaces for account provisioning, queue commands, appointment commands, history and admin operations, with typed DTOs/results and server validation. Do not implement FirebaseBackend as the old synchronous DemoRepository or default to empty “success” data. Thread/lifecycle/cancellation/pagination/live listeners must be designed at each feature migration; no process-global listener is installed now.

Android callable limitation: the Functions SDK requires IID and attempts token acquisition from non-emulated FCM/Installations. With deliberately non-production local options, the call fails its API-key precondition. Removing IID registration also breaks Functions component dependencies, so standard SDK registration is retained. Android tests cover local Auth and Firestore; Node tests verify the Functions emulator probe. Android callable/FCM verification awaits genuine configuration and reviewed notification/consent behavior. No fake production key or substitute IID implementation is used.
